# Phase-01.2 — Intake UX + Runtime Time Context

Version: v0.2  
Status: Active Planning  
Parent Phase: Phase-01.1 Runtime + Intake Closure  
Runtime Foundation: DeepAgents SDK

---

# 1. Purpose

Phase-01.1 closed the core Intake chain:

```text
Raw User Input
  -> Redactor
  -> Intake Agent
  -> LLM structured JSON
  -> normalize_request
  -> Request Guardrails
  -> Router-ready NormalizedRequest
```

Phase-01.2 focuses on two remaining Intake-level problems:

1. **Blocked request UX**  
   When Request Guardrails blocks a request, the CLI currently reports internal field names but does not provide a sufficiently human-readable explanation or supplement path.

2. **Runtime time context**  
   Relative time expressions such as `今天`, `昨天`, `最近1小时`, `近24小时` must be resolved from runtime-provided current time. The LLM must not invent dates.

This phase is still part of Runtime + Intake. It must not implement Evidence Pipeline, MySQL collection, MySQL analysis, findings, validation verdicts, FastAPI, MCP, or document rendering.

---

# 2. Phase Goal

Build a safe, usable, and LLM-assisted Intake UX.

This phase must ensure:

- Runtime injects current datetime, timezone, and locale into Intake Agent.
- Intake Agent uses runtime time context for relative time expressions.
- LLM does not invent current dates.
- Blocked requests produce human-readable messages.
- Human-readable blocked messages are generated by LLM as **structured `user_message`**, not by Runtime hardcoded business enumeration.
- Runtime validates and renders structured `user_message`.
- Runtime never prints raw LLM prose directly.
- Interactive supplement is supported.
- User supplement text is redacted first, then interpreted by Intake Agent into structured `supplement_patch`.
- Runtime validates and merges `supplement_patch`.
- Raw secrets never enter LLM, artifacts, telemetry, or logs.

# 5. Runtime Time Context

## 5.1 Runtime Context Injection

Runtime must inject time context into each Intake Agent call.

Required structure:

```json
{
  "runtime_context": {
    "current_datetime": "2026-05-08T10:30:00+08:00",
    "timezone": "Asia/Shanghai",
    "locale": "zh-CN"
  }
}
```

Minimum config:

```yaml
runtime:
  timezone: Asia/Shanghai
  locale: zh-CN
```

If timezone is not configured, Runtime may use the local system timezone, but it must record the resolved timezone in telemetry.

## 5.2 Relative Time Handling

`skills/intake/SKILL.md` must explicitly state:

```text
Use runtime_context.current_datetime and runtime_context.timezone to resolve relative time expressions.
Never invent current dates.
If runtime_context is missing, mark runtime_context.current_datetime as missing.
```

Relative expressions include at minimum:

```text
今天
昨天
刚才
最近1小时
近24小时
前1小时
后1小时
今晚
上午/下午/晚上
```

## 5.3 Time Normalization Boundary

LLM/Skill decides semantic meaning.

Allowed Runtime/Tool behavior:

- validate ISO datetime
- convert relative components to concrete ISO datetime using runtime_context
- calculate `time_window.start/end` from LLM-provided `before/after`
- enforce timezone consistency

Forbidden Runtime behavior:

- invent current date
- hardcode DBA business defaults
- define default before/after policy outside skills

## 5.4 Example

Input:

```text
今天17:00触发 mysql cpu usage > 85%
```

Runtime context:

```text
current_datetime=2026-05-08T10:00:00+08:00
timezone=Asia/Shanghai
```

Expected:

```json
{
  "event_time": "2026-05-08T17:00:00+08:00",
  "time_window": {
    "before": "6h",
    "after": "1h",
    "start": "2026-05-08T11:00:00+08:00",
    "end": "2026-05-08T18:00:00+08:00",
    "source": "skill_default_from_event_time"
  }
}
```

Do not output invented dates such as:

```text
2025-07-15
```

# 6. Blocked Request UX

## 6.1 Problem

Current blocked output is technically correct but too internal:

```text
status=blocked
reason=missing_required_fields
missing_fields=target.host,ssh_target.host,ssh_target.username
```

This is insufficient for users.

## 6.2 Correct Design

Human-readable blocked messages must be generated by Intake Agent as structured output.

Runtime must not try to enumerate every business scenario itself.

Correct flow:

```text
Request Guardrails blocked
  -> Intake Agent generates structured user_message
  -> Runtime validates user_message
  -> Runtime renders validated user_message
  -> Runtime writes blocked artifact + telemetry
```

## 6.3 Do Not Print Raw LLM Prose

Runtime must not directly print raw LLM response.

Reason:

- raw LLM prose may contain unsupported assumptions
- raw LLM prose may include chain-of-thought-like content
- raw LLM prose may leak internal field names or unvalidated content
- CLI output must be stable, auditable, and secret-safe

Allowed:

```text
LLM structured user_message
  -> Runtime schema validation
  -> Runtime secret leakage check
  -> Runtime rendering
```

Fallback:

```text
If user_message is missing or invalid, Runtime may render a simple deterministic fallback from missing_fields.
```

# 7. Structured `user_message` Contract

## 7.1 Required Shape

Intake Agent may output:

```json
{
  "user_message": {
    "summary": "当前请求需要补充 MySQL 主机地址后才能继续。",
    "missing_items": [
      {
        "field": "target.host",
        "label": "MySQL 主机地址",
        "reason": "你希望 DBKit 直接连接 MySQL 进行 live collection，但没有提供连接目标。",
        "example": "192.168.1.10"
      }
    ],
    "retry_example": "请帮我分析 192.168.1.10 的 MySQL，账号 root，今天17:00触发 mysql cpu usage > 85%。"
  }
}
```

## 7.2 Validation Rules

Runtime must validate:

- `summary` exists and is string
- `missing_items` is list
- each item has `field`, `label`, `reason`, `example`
- `field` must correspond to actual blocking missing fields or blocking issues
- no raw secrets are present
- no markdown fences
- no chain-of-thought-like text

## 7.3 Rendering Rules

Runtime may render validated `user_message` as:

```text
DBKit intake blocked.

原因：
当前请求需要补充 MySQL 主机地址后才能继续。

缺少信息：
- MySQL 主机地址
  原因：你希望 DBKit 直接连接 MySQL 进行 live collection，但没有提供连接目标。
  示例：192.168.1.10

你可以这样补充：
请帮我分析 192.168.1.10 的 MySQL，账号 root，今天17:00触发 mysql cpu usage > 85%。

artifact=.dbkit/artifacts/req_xxx.blocked-request.json
```

## 7.4 Fallback Rendering

If `user_message` is absent or invalid, Runtime must render a deterministic fallback:

```text
DBKit intake blocked.

缺少必要信息：
- target.host

artifact=.dbkit/artifacts/req_xxx.blocked-request.json
```

Fallback is allowed but should be considered degraded UX.

# 8. Interactive Supplement Flow

## 8.1 Purpose

Interactive supplement allows the user to continue from a blocked request by providing missing information.

This is not production action approval.  
This is only Intake missing-field completion.

## 8.2 Configuration

Config option:

```yaml
runtime:
  interactive: true
```

Optional CLI flag:

```bash
dbkit ask --interactive "..."
```

## 8.3 Correct Flow

```text
Request Guardrails blocked
  -> Intake Agent produces structured user_message
  -> Runtime renders validated user_message
  -> User enters supplement text
  -> Runtime Redactor sanitizes supplement text
  -> Intake Agent interprets supplement text
  -> Intake Agent outputs supplement_patch
  -> Runtime validates supplement_patch
  -> Runtime merges supplement_patch into NormalizedRequest
  -> Request Guardrails rerun
  -> pass or block again
```

## 8.4 Important Boundary

Runtime must not hardcode semantic field assignment for supplement text.

Runtime should not assume:

```text
first answer = target.host
second answer = ssh_target.username
```

Instead, supplemental text must be interpreted by Intake Agent.

Example user supplement:

```text
MySQL 是 192.168.1.10，SSH 也是这台机器，用户 root
```

Expected Intake Agent `supplement_patch`:

```json
{
  "target": {
    "host": "192.168.1.10"
  },
  "ssh_target": {
    "host": "192.168.1.10",
    "username": "root"
  }
}
```

Runtime validates and merges this patch.

# 9. `supplement_patch` Contract

## 9.1 Required Shape

Intake Agent may output:

```json
{
  "supplement_patch": {
    "target": {
      "host": "192.168.1.10"
    },
    "ssh_target": {
      "host": "192.168.1.10",
      "username": "root"
    },
    "provided_evidence": {
      "files": [
        "/workspace/tmp/mysql-error.log"
      ]
    }
  }
}
```

## 9.2 Validation Rules

Runtime must validate:

- patch only modifies allowed fields
- patch cannot insert raw secrets
- patch cannot change `target_agent` to a system agent
- patch cannot bypass `collection_policy`
- patch cannot enable live collection if user explicitly disallowed it
- patch cannot mutate unrelated existing values without clear supplement intent
- patch merge must be recorded in telemetry
- Request Guardrails must rerun after patch merge

## 9.3 Secret Supplements

If user supplement contains secrets:

```text
密码是 Root@123
```

Runtime must redact first:

```text
密码是 <SECRET_REF:...>
```

LLM only sees `secret_ref`.

Raw secret must not appear in:

- LLM input
- artifact
- telemetry
- logs
- traces

```text

  -> validate
  -> secret check
  -> render
```

If invalid:

```text

```

## 11.4 Supplement Handler

Add interactive supplement handler:

```text

  -> collect supplement text
  -> redact supplement text
  -> call Intake Agent in supplement mode
  -> parse supplement_patch

  -> merge patch
```

# 15. Success Criteria

Phase-01.2 is complete when:

1. Runtime injects current datetime, timezone, and locale into Intake Agent.
2. Intake no longer invents dates for relative time expressions.
3. `今天17:00` resolves using runtime context.
4. Blocked requests produce human-readable CLI output.
5. Human-readable output is generated from validated structured `user_message`, not raw LLM prose.
6. Runtime fallback rendering works when `user_message` is invalid or missing.
7. Interactive supplement collects user input and sends redacted supplement text to Intake Agent.
8. Intake Agent produces structured `supplement_patch`.
9. Runtime validates and merges `supplement_patch`.
10. Request Guardrails rerun after supplement merge.
11. Secret supplements remain secret-safe.
12. Artifacts remain machine-readable and secret-safe.
13. Telemetry records blocked UX, runtime time context, supplement, and patch events.
14. Required tests pass.
15. GitHub CI passes.
